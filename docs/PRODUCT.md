# 产品需求文档（框架）

## 1. 产品概述

**暂定名称：** 善款账本
**产品定位：** 面向公益项目的分阶段捐款托管与共同审批工具。通过智能合约约束拨款条件，并为每次拨款关联可追踪的执行凭证。

## 2. 背景与问题

捐赠者通常难以持续确认善款何时拨出、由谁批准、款项是否按计划执行。单纯公开收支表不能阻止项目管理方提前支取或绕开约定流程。本产品将“赞成票超过登记捐款地址的 50%、反对票低于 30%，且上一笔完成后才能申请下一笔”编码为链上状态约束。

## 3. 目标与非目标

**目标**

- 项目资金由合约托管，拨款金额和收款地址公开可验证。
- 每笔拨款必须同时满足赞成票严格超过全部登记捐款地址的 50%，且反对票严格低于 30%。
- 上一笔拨款转出后，项目负责人提交执行凭证摘要，合约才开放下一笔。
- 捐款者可查看项目、审批状态、链上交易和凭证记录。

**首期非目标**

- 不自动判断发票、照片或现实采购行为是否真实。
- 不提供法币支付、税务收据、跨链资产或 DAO 治理。
- 不以链上记录替代公益组织的审计和法律合规义务。

## 4. 用户与权限

| 用户       | 主要能力                                                     |
| ---------- | ------------------------------------------------------------ |
| 捐款者     | 捐款、查看明细、对每笔提案批准或拒绝（首期暂不支持撤回批准） |
| 项目负责人 | 建立项目、提出拨款、执行合约拨款、提交执行凭证               |
| 公众访客   | 查看项目进展、链上交易和公开凭证                             |
| 平台运营   | 项目准入、内容治理、风险处置；不应具备绕过合约提取资金的权限 |

## 5. 核心流程

1. 项目部署资金合约，捐款者向合约捐款并成为该项目的登记捐款者。
2. 项目负责人提交拨款提案，明确金额、收款地址、用途说明和审批材料摘要；提案期间暂停新捐款，确保审批集合稳定。
3. 登记捐款者对同一提案投赞成或反对票。只有赞成票超过 50% 且反对票低于 30% 时，合约才允许拨款；反对票达到 30% 或投票结束仍未达标时，提案被拒绝。
4. 达到阈值后，项目负责人调用合约，将批准的金额转给提案收款地址。
5. 负责人提交执行凭证（例如发票、收货记录、现场报告）的内容哈希及链下访问地址。
6. 凭证提交后合约才开放下一笔拨款申请；捐款者重新对下一笔提案一致审批。

## 6. 首期功能范围

### 前端（React）

- 项目总览、募集与已执行金额、捐款者列表。
- 分笔拨款时间线、提案详情、审批进度和交易状态。
- 钱包连接、网络提示、签名确认及交易失败/待确认状态（后续接入）。
- 执行凭证展示与链上哈希校验入口。

### 后端（Python）

- 项目元数据、捐款者展示信息与凭证索引 API。
- 监听链上事件并同步项目、捐款、提案和审批状态。
- 凭证上传、访问控制、恶意文件检查与哈希计算。
- 管理后台认证、审计日志、限流与数据备份。

### 智能合约（Solidity）

- 接收捐款并记录捐款者集合。
- 按序提出拨款、记录每个地址一票的赞成/反对、验证严格投票阈值。
- 仅在赞成票 >50% 且反对票 <30% 后向指定收款人拨款。
- 拨款执行后，只有负责人提交非空凭证摘要才能进入下一笔。
- 事件索引、权限边界、重入和失败转账处理。

## 7. 关键业务规则（待确认）

- 投票分母是提案时的登记捐款地址数，每个地址一票，不按捐款金额加权；同一主体使用多个地址可能拥有多票。
- 提案投票期间暂停新捐款，固定投票分母。反对达到 30% 或所有地址投票但赞成票不超过 50% 时，当前提案被拒绝，项目负责人可重新提交同一笔次提案。
- 合约只能保证资金转账与流程状态，不能证明转账后的线下用途真实。执行凭证由负责人提交，需要公众审核、第三方审计或争议机制补足。
- 当前示例使用原生链上资产；正式部署前需确定链、代币、退款规则、手续费和资产托管主体。
- 地址身份未合并可能造成多地址重复投票；阈值投票也无法替代实名治理。提案超时、退款或紧急治理机制仍需法律与业务共同评估。

## 9. 成功指标

- 每笔拨款从提案到链上执行的可追溯率。
- 执行凭证按时提交率及凭证可访问率。
- 捐款者审批参与率、提案平均审批时长和未完成提案比例。
- 资金差异、未经授权拨款和凭证争议事件数量。

## 10. 风险与依赖

- 合约漏洞可能造成资金不可逆损失；上线前需独立审计、测试网演练和应急预案。
- 负责人提交的哈希只证明某份内容未被替换，不证明内容真实或完整。
- 捐款者地址与个人身份的映射涉及隐私；默认不公开个人信息，链上只保存地址和必要事件。
- 钱包丢失、地址重复或恶意反对仍可能阻塞拨款；需要评估地址身份绑定、提案超时与退款机制。
- 需确认目标司法辖区下的募捐资质、资金托管、退款、个人信息和电子凭证要求。

## 11. 里程碑

1. 项目骨架与本地工作流原型（当前）。
2. 明确链、资产、身份与审批规则；完成合约单测和威胁建模。
3. 接入钱包、合约部署与链上事件索引，完成测试网闭环。
4. 完成凭证服务、权限审计、合约审计及小范围试点。

## 12. 待产品/业务确认

- 首期按捐款地址一票。是否改为实名主体/捐款份额加权，以及同一主体多个钱包如何合并？
- 是否允许负责人或关联方捐款并参与批准？
- 项目失败或审批长期未达成时，退款由谁发起、如何表决？
- 凭证谁能查看、保留多久、如何处理个人信息和争议？
- 采用公链还是许可链，使用原生资产还是稳定币？

## 14. 当前本地链 MVP 实现说明

本节记录 2026 年 11 月 13 日最终验收后的实际实现，用于区分已经可演示的 MVP 与后续完整产品规划。

### 14.1 当前演示范围

- 使用一个固定演示项目 `Mountain School Water Access`，项目编号为 `PF-2025-018`。
- 使用本地 Anvil 和测试 ETH，Chain ID 为 `31337`。
- 配置一个 Manager 和两个捐赠者账户：Donor A、Donor B。
- 页面以固定演示汇率 `1 ETH = 2,000 USD` 显示金额，链上实际结算仍为 test ETH。
- 当前目标是一次完整、可重复的本地链产品演示，不包含项目发布、多项目或正式生产部署。

### 14.2 角色权限

| 角色 | 当前可见内容 | 当前可执行操作 |
|---|---|---|
| Manager | Funding Projects、Donors、Approval Flow、Fund Contract | 提交带审批材料的提案、查看投票状态、执行已批准拨款、提交执行凭证、查看被拒绝提案通知 |
| Donor A / Donor B | Funding Projects 项目页 | 在 Funding 阶段捐款；在活动提案中打开审批材料、核验哈希并投票一次 |
| 未连接钱包的访客 | 公共项目概览和钱包连接入口 | 连接钱包 |
| 已连接但未登记的地址 | 公共项目概览和捐款入口 | 在 Funding 阶段捐款并登记为捐赠者 |

Manager 的前端页面不显示捐款表单，避免角色操作混淆。当前合约层尚未禁止 Manager 直接调用 `deposit()`，属于已记录的 MVP 限制。

### 14.3 完整业务流程

1. Manager 或捐赠者连接浏览器钱包，并切换到 GoodFund Localhost。
2. Donor A 和 Donor B 分别向合约捐款，合约按地址登记捐赠者。
3. Manager 提交拨款提案，填写收款地址、美元展示金额、用途说明和审批材料。
4. 前端计算审批材料的 SHA-256，提案在链上保存用途、材料哈希和材料访问标识。
5. 提案期间新捐款暂停，确保投票分母稳定。
6. 捐赠者在投票前打开审批材料并核验文件哈希。
7. Donor A 和 Donor B 分别使用自己的钱包投票，每个地址对同一提案只能投一次。
8. 赞成票严格超过全部登记捐赠地址的 50%，且反对票严格低于 30% 时，提案进入 `Ready to disburse`。
9. 如果反对票达到 30%，或全部登记地址投票后仍未达到批准阈值，提案被拒绝。
10. Manager 只有在 `Ready to disburse` 状态下才能把获批金额转给提案收款地址。
11. 拨款完成后，Manager 提交执行凭证的 SHA-256 和访问标识，合约才把 current tranche 加一。
12. 下一 tranche 进入 Funding 状态，可以继续提交新的资金申请。

### 14.4 链上规则

- 投票权重为一地址一票，不按捐款金额加权。
- 阈值分母是全部已完成登记的捐赠地址数，而不是当前已投票地址数。
- 同一地址在同一提案中不能重复投票，也不能修改已记录的投票。
- 提案被拒绝时，提案金额、收款地址、审批材料、赞成票和反对票会清空，current tranche 不增加。
- 提案被拒绝后，合约发出 `PayoutRejected` 事件。Manager 页面从事件读取最近一次拒绝结果，并显示提案编号、用途、金额、票数、原因和交易哈希。
- 拨款执行后，未提交非空执行凭证哈希和访问标识时不能申请下一笔。
- 执行凭证提交后，合约发出 `ExecutionReported` 事件并开放下一 tranche。

### 14.5 审批材料与执行凭证

审批材料用于说明“这笔钱准备怎么使用”，必须在捐赠者投票前可见。当前实现把用途说明、材料 SHA-256 和材料访问标识写入提案。

- 内置样例材料：`/evidence/procurement-quotation.svg`
- 捐赠者可以打开材料，并重新计算 SHA-256 与链上值比较。
- 本地自定义上传文件限制为 750 KB，并保存在当前浏览器；跨浏览器演示应使用内置样例。

执行凭证用于说明“这笔钱已经用于约定用途”，必须在拨款后提交。当前 MVP 统一使用内置样例文件 `/evidence/water-source-assessment.svg`，把文件的 SHA-256 和公开访问标识写入合约。Manager 与捐赠者都可以打开凭证并重新计算哈希与链上值核对。文件内容保存在前端静态目录，不保存在钱包、合约或 IPFS 中。该哈希不证明文件内容真实，也不证明线下采购或交付已经发生。

### 14.6 当前 MVP 不包含

- 项目创建和发布页面。
- 多项目选择、项目工厂合约或项目目录。
- 投票截止时间、自动超时处理和退款。
- 真实法币、稳定币、价格预言机和资金兑换。
- 审批材料和执行凭证的 IPFS、对象存储或完整后端上传服务。
- 完整链上事件索引、块浏览器和正式站内通知。
- 多签 Manager、管理员转移和密钥恢复。
- Sepolia 或其他测试网部署。
- 面向生产环境的合约审计、合规审查和身份认证。

### 14.7 当前验收结论

- 主成功流程已完成：双人捐款、材料提案、50% 未通过、第二票通过、执行拨款、凭证提交和开放下一 tranche。
- 关键失败路径已完成：重复投票、反对票达到阈值、超余额提案、未达门槛执行和未交凭证继续提案。
- 角色隔离已完成：Manager 不显示捐款表单，捐赠者不显示提案和拨款控制。
- 当前实现适合课程项目的本地链 MVP 演示，不应描述为已经完成生产级公益资金平台。
